# 5단계 · 다듬기와 성능

## 잰 것 (`npm run perf`)

헤드리스 Chromium(SwiftShader), 데모 사진 24장. "×4"는 CPU를 4배 느리게 해 보통 휴대폰을 흉내 낸 값.

| | 전 | 후 |
|---|---|---|
| 첫 화면이 조각보를 펼치기까지 | 1.31초 (×4: 2.47초) | 0.56초 (×4: 1.38초) |
| 색 뽑기 24장 (Node) | 350ms | 47ms |
| 빛 모드에서 손을 따라 빛이 움직일 때 한 프레임 (×4) | 100ms (10fps) | 33ms (30fps) |
| PNG 3000px 만들기 | 1.5초 | 1.5초 (그대로) |

## 고친 것과 이유

- **k-means를 평평한 배열과 제곱 거리로**: 거리는 크기 비교에만 쓰이니 제곱근이 필요 없다. 피드 한 장에 사진이 백 장 넘게 오면 이 부분이 기다리는 시간의 대부분이라 7배 줄였다. 결과는 같다 (단위 테스트 그대로 통과).
- **sRGB → 선형 값 미리 풀어 두기**: 8비트 값은 256가지뿐이다.
- **데모 사진은 브라우저가 줄인다**: 큰 그림을 픽셀로 다 꺼낸 뒤 JS로 줄이지 않고, 240px로 그리면서 바로 줄인다.
- **빛 모드 층 나누기**: 창 빛은 천을 곱으로 지나간다 (빛 × 천). 그래서 천과 실을 한 번 떠 두면, 빛만 움직일 때는 창 → 떠 둔 천 곱하기 → 실 순서로 세 장만 겹치면 같은 그림이 된다. `e2e/demo.spec.ts`가 매번 새로 그린 그림과 픽셀 단위로 비교한다 (평균 차이 0.6/255 미만). 큰 PNG를 만들 땐 메모리를 두 배로 쓰므로 끈다.
- **창에 걸었을 때 원본 사진도 곱하기로**: 역광에서 사진은 슬라이드 필름처럼 빛을 거른다. 층 나누기와도 맞는다.
- **같은 조각 위에서 마우스가 움직일 땐 다시 그리지 않기**: 바뀐 게 없으면 그리지 않는다.

## 다듬은 것과 이유

- **넓은 화면에선 조각보를 왼쪽에 세우고 소개·손짓을 옆에**: 꿰매는 동안 남은 솔기 수와 버튼이 늘 보여야 하고, 조각보 전체가 한 화면에 들어와야 어디를 꿰맬지 보인다 (화면 높이에 맞춤).
- **기기에 맞는 안내만**: 마우스가 있으면 "올리면", 손가락뿐이면 "길게 누르면". 없는 손짓을 안내하지 않는다.
- **버튼 높이 44px**: 손가락으로 누르기 넉넉한 높이.
- **움직임 줄이기 설정 존중**: 조각이 미끄러지는 대신 바로 제자리. 뜻(붙었다)은 같고 움직임만 뺀다.
- **아이폰 노치·홈 바 여백(safe-area)**, 주소창 색을 한지 색으로 (`theme-color`).
- **아이콘**: 네 조각과 꿰매는 중인 붉은 시침실 하나.
- **"사진은 이 브라우저 밖으로 나가지 않아요"**: 사진을 올리기 전에 알아야 할 단 하나의 약속.
- **공용 스타일 분리**: 모든 화면이 쓰는 바탕(`src/app/base.css`)을 1단계 확인 화면 스타일에서 떼어 냈다.

## 아직 못 한 것

- 실제 아이폰·안드로이드에서 터치와 속도 확인 (여기 숫자는 에뮬레이션).
- 화면을 돌리거나 창 크기를 바꾸면 캔버스는 CSS로만 늘고 해상도는 처음 그대로.
- 3000px PNG가 약 20MB. 천의 결이 촘촘해 압축이 잘 안 된다.
